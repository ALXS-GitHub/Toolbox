# Developing on Roblox

Roblox Studio is a very good 3D world editor, but a limited code editor: no git, no real quality tools, and an AI agent
can only work in it through an MCP server. For [Pack a K-Pop Idol](/projects/pack-a-kpop-idol) I therefore split the
two: **code lives as files in a git repository, 3D lives in Studio**, and Rojo bridges them. This guide describes that
toolchain, reusable for any game.

## The toolchain

| Tool | Role |
|---|---|
| **Rokit** | installs and pins the other tools, one version per project |
| **Rojo** | syncs Luau files from disk into Studio |
| **Wally** | package manager (React Lua, an animation library) |
| **Selene** | Luau linting, with Roblox's standard library |
| **StyLua** | automatic formatting |
| **Luau LSP** | completion and types in VS Code, thanks to the project map generated by Rojo |

Rokit is the only tool installed globally. The others are listed with their version in a `rokit.toml` at the game's
root: anyone (or any agent) opening the project gets exactly the same versions with `rokit install`. On the editor side,
the VS Code extensions for Rojo, Luau LSP, Selene and StyLua complete the set.

## Code as files, 3D in Studio

Rojo's project file maps each Roblox service to a folder: server code, client code, shared modules, Wally packages.
Rojo only syncs code; everything else — scenery, lighting, models, assets — stays in the game file, which git does not
track. That choice avoids conflicts and keeps the repository light, and Rojo is set never to delete in Studio what it
does not know about.

Sync goes **one way**, from disk to Studio. The golden rule follows: never edit code in Studio, or Rojo overwrites it.
If needed, `rojo syncback` brings back an exceptional change made in Studio.

## A working session

```bash
cd game
rojo serve          # Studio then connects with the Rojo plugin
```

1. Open the game in Studio and connect the Rojo plugin.
2. Start [Claude Code](/setup/claude-code) at the repository root, and work in the files.
3. Test in Studio: F5 solo, F6 with several players.
4. Before committing, `selene src/` and `stylua src/`, then `rojo build`, which checks that the project builds.

The game's interface is written with React Lua, a real React (components and hooks) ported to Luau: it is described in
code instead of being built by hand in Studio.

## Claude Code and the Studio MCP

The agent works on the files like on any project. For what is not code, it goes through the **official Roblox Studio
MCP server**: run Luau in Studio, inspect or change objects, insert an asset, start a test and read the console, take a
screenshot. The rule is strict: never code through the MCP, since Rojo would overwrite it on the next change.

Recurring tasks are written as skills in the project repository: create a service or a controller, create an
interface, add a group, review the code, publish. Several Claude Code sessions can work on the same repository at once;
each one's rule is to add its files to the commit explicitly, never taking another one's work.

## Testing and publishing

Risky experiments happen in a separate **sandbox game**, set up with the same tools and another Rojo port: it can read
the main game, never change it. Publishing follows a procedure, also written as a skill: checks, commit and version
tag, then saving and publishing from Studio, and finally restarting the servers from Roblox's dashboard so players get
the new version.
